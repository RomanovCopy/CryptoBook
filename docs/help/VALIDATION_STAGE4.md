## Подтверждённые различия форматов

| Формат | Фактический результат |
| --- | --- |
| RTF | После Save As и открытия другого файла → повторного открытия сохранены `Format Ж Є ä` и полужирное начертание; начало файла `7B5C72746631` |
| XamlPackage | Сохранены тот же текст и полужирное начертание; ZIP-пакет начинается `504B0304` |
| XAML | Тот же текст, полужирное начертание потеряно. XamlTextDocumentFormatHandler использует DataFormats.Text |
| TXT | Тот же текст, полужирное начертание потеряно. Фактический UTF-8 без BOM, начинается байтами текста `466F726D617420D09620D084` |
| Markdown | Отдельный исходник, не снимок предпросмотра. Для UTF-8 без/с BOM, UTF-16 LE/BE и UTF-32 LE/BE после Save совпадают ожидаемые байты, BOM и CRLF; новые шаблоны Markdown создаются UTF-8 без BOM |

Нельзя выводить кодировку сохранения из DefaultEncoding шаблона: реальную запись определяет обработчик. MarkdownTextCodec проверен также по исходникам: без BOM ожидается UTF-8, ошибочное декодирование переходит к UTF-8 с возможной заменой символов. Произвольный выбор кодировки и обратный экспорт оформленного документа в Markdown интерфейс не предоставляет. Потеря оформления не сопровождается гарантированным отдельным предупреждением; статьи предупреждают до действия.

Поддержка встроенных изображений, фона и параметров страницы дополнительно покрыта существующими DocumentFormatHandlerTests/DocumentTemplateTests. Это не проверка совместимости сложной вёрстки с внешним офисным редактором. Защищённый контейнер описан по текущим обработчикам и существующим тестам политики; новая аппаратная/ключевая проверка остаётся этапу 8.

## Сценарии и изоляция

[HelpValidation](../../tools/HelpValidation/README.md) использует производственный App.OnStartup, Autofac, XAML, команды и реальные записи только в новой расходной папке. Properties.Settings заранее переведены в MemorySettingsProvider; JSON/index/recovery/lock переназначены. Миграция, IPC, обновления и загрузка модели не запускаются. На этапе 4 мониторинг каталогов отключён; статическая цепочка предков даёт файловому менеджеру путь к Demo без перечисления соседних папок. Реальные файлы списка и предпросмотр берутся с диска из Demo.

Проверены выбор рабочего пространства и его отображение в настройках; применение шаблона по умолчанию в следующем диалоге; создание встречи; недоступное назначение; повтор без перезаписи существующего файла. Все шесть шаблонов создаются на диске и открываются в RTF/TXT/Markdown. Четыре формата проходят Save As, уход на другой файл и повторное открытие с проверкой Unicode и оформления.

Уточнена методика старого сценария: OpenAsync уже активного пути мог лишь вернуть существующую сессию, поэтому сам по себе не доказывал чтение записанных байтов. Повторный `verify` каркаса теперь закрывает сохранённый RTF перед открытием; форматные сценарии этапа 4 открывают другой файл, затем проверяемый. Исходные кадры этапа 3 оставлены как изображения интерфейса; подтверждение фактического повторного чтения дают новые отчёты.

Отмена Save As сохраняет путь, ревизию, dirty и текст. Реальная блокировка FileShare.Read вызывает ошибку записи: прежние байты файла и редактируемый текст остаются. Попытка Save при Close с этой ошибкой не закрывает документ; повтор после снятия блокировки успешен. Настоящий файловый менеджер открывает выбранный файл; настоящий WPF-пикер папки проверен на подтверждение и отмену.

Обычный документ и Markdown одновременно изменены, переходы сохраняют независимые пути/тексты/dirty. Сохранение Markdown оставляет обычный документ изменённым. Проверка выхода видит изменения неактивного редактора и при отмене восстанавливает активный. Проверены отмена замены, отмена Close, Save+Close, Discard+Close и сохранность второго редактора. Переименование выполнено командой бокового меню через реальный TextInputDialog с сохранением расширения.

Важная граница: назначения нативного SaveFileDialog и ответы нативных вопросов UnsavedChanges задаются явными очередями тестовых IDocumentSaveTargetPicker/IDocumentDialogService. Это проверяет производственные конвейеры после решения пользователя, но не физический ввод/фильтры/подтверждение перезаписи Windows. В статьях эти элементы сверены по owning source DocumentSaveTargetPicker/WpfDocumentDialogService. Нет подмены снимков этими очередями: кадры содержат настоящие видимые WPF-представления и настоящую ошибку файловой записи.

TEMP/TMP только процессов проверки направлены в `artifacts/help-stage4-temp`; SDK при restore/build потребовал доступ к реестру Windows SDK за пределами sandbox. Restore выполнен в locked mode, версии пакетов и lock не менялись. Пользовательские настройки не загружались для демонстрации, не сохранялись и не «восстанавливались» задним числом. База Git/версия не менялись, публикация и отправка не выполнялись.

## Оставшиеся границы и следующий этап

Не проверялись физические клавиатура/мышь, изменение Windows DPI/мониторов, установленный пользовательский профиль/миграция, новое шифрование с ключом, Android, PDF/внешние ассоциации, реальные медиа и принтер. Для полноты доставки остаётся этап 12; новое окно и ресурсы уже проверяются из постороннего CWD без исходных статей рядом. Поставка/установщик не создавались.

Отдельно зарегистрирован Q11: некорректное имя при создании может уйти в AutoRename со стандартным свободным именем. Статья требует проверять фактическое имя; строгая валидация остаётся тематике файлового менеджера, а не скрывается под видом проверенного отказа.

Следующий отдельный этап — **5: редактор, содержимое и Markdown**. До удаления MarkdownSyntaxHelp перенести все её группы и примеры в четыре версии md.syntax/md.edit/md.preview и проверить прямой вход. Этап 5 автоматически не выполнялся.
