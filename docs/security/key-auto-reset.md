# Сброс ключа и восстановление защищённой работы

Актуализировано 1 ноября 2026 года по AutoKeyResetService, LockSnapshotService, DocumentRecoveryService и проверкам этапа 8. Прежний документ был проектным заданием и ошибочно обещал блокировку любых обычных документов и сохранение ключа при сбое снимка. Ниже описано действующее поведение. Пользовательские инструкции: [сброс ключа](../help/content/ru-RU/security.lock.md), [lock-снимок](../help/content/ru-RU/recovery.lock.md), [аварийная копия](../help/content/ru-RU/recovery.crash.md).

## Область действия

- Ключ шифрования — не пароль входа в приложение. Если открыты только обычные документы, сбрасывается ключ; документы и несохранённая работа остаются доступны. Снимок блокировки для них не создаётся.
- Для защищённого активного или скрытого документа создаётся и проверяется снимок под прежним паролем, затем ключ очищается. Когда защищены оба редактора, сохраняются оба; при одном защищённом документе обычный сосед остаётся в рабочем пространстве.
- Успешный сброс освобождает обычную работу. Восстановление сохранённого lock-снимка вызывается только вручную через боковое меню → Файл → Восстановить снимок после сброса ключа.
- При ошибке создания/проверки снимка ключ также очищается, а защищённая несохранённая работа удерживается скрытой в памяти. Экран блокировки не допускает доступа к ней и штатного закрытия до проверки прежнего ключа. Проверка использует независимое защищённое подтверждение, если снимок недоступен. Такой процесс нельзя завершать до разблокировки и сохранения нужной работы.

## Причины сброса

Ручные Ctrl+L главного окна/настроек и «Сбросить ключ сейчас». При наличии ключа — бездействие 1/5/10/15/30 минут, по умолчанию 15; «Никогда» отключает только таймер. Значение применяется без перезапуска. Потеря фокуса сама по себе не сбрасывает ключ.

События блокировки/завершения Windows-сеанса, удалённого отключения и перехода в сон направляются в тот же безопасный сценарий. Действия внутри приложения обновляют время активности. Длительные файловые операции используют Pause; отложенное срабатывание повторно проверяет состояние, активность и текущие настройки. Физическая блокировка Windows/сон не выполнялись ради съёмки: разделение подтверждения статическим кодом, сервисными тестами и живыми WPF-командами указано в [отчёте](../help/VALIDATION_STAGE8.md).

## Lock-снимок

Путь по умолчанию: `%LOCALAPPDATA%\CryptoBook\Lock\last.lock.cbook`. Снимок сериализует содержимое в памяти, хранит метаданные и при необходимости второй документ в защищённом контейнере. Исходный обычный файл не заменяется. При замене снимка сохраняется предусмотренный сервисом pending-путь; пароль и открытый текст в служебное уведомление не записываются. Отдельная .notice защищает отображаемые имена/пути средствами текущего Windows-пользователя; она не даёт доступ к содержимому без ключа CryptoBook.

При запуске и после успешного сброса уведомления о сохранённых снимках не показываются. Восстановление открывается только командой бокового меню → Файл → «Восстановить снимок после сброса ключа». Без снимка команда недоступна. При удержанной в памяти работе используется кнопка «Разблокировать» экрана блокировки.

Ввод ключа — одно скрытое поле, проверка до доступа, задержка между неудачными попытками. Правильный ключ приводит к выбору:

- «Открыть» — сохранённый исходный файл, если доступен;
- «Восстановить снимок» — несохранённое содержимое снимка как изменённый документ;
- «Отмена» — сохранить снимок для следующей попытки. После уже успешной проверки ключ остаётся установленным.

При недоступном исходнике предлагается восстановление снимка. После успешного восстановления снимок удаляется. Для обоих редакторов регистрируются доступные страницы без промежуточной навигации к неактивной: на экране должен отображаться действительно активный возвращённый документ.

## Аварийная копия и .bak — отдельно

`.bak` рядом с исходником — предыдущая успешная версия сохранения. Её восстановление не пишет на диск до явного решения пользователя. При смене ключа несовместимая защищённая .bak синхронизируется с текущим файлом, поэтому это не гарантия более раннего текста.

Текущий аварийный снимок хранится в Recovery пользовательских данных. При запуске прошлая копия откладывается отдельно; обычная работа не требует обязательного диалога. Команда бокового меню → Файл → «Восстановить несохранённые изменения» возвращает последнюю отложенную копию после решения по текущим изменениям. Новый формат защищённых снимков требует исходного пароля CryptoBook, обычные копии — доступа от соответствующей Windows-учётной записи. Ранее созданные DPAPI-копии продолжают читаться по старым правилам, в том числе если они содержали когда-то защищённую работу; новый пароль не изменяет существующие копии. После возврата новая аварийная копия записывается до удаления использованной отложенной. При неверном ключе, отмене или ошибке новой записи старая копия остаётся.

## Границы подтверждения

Алгоритмы шифрования, правила нового пароля и аутентификация снимков не ослаблялись. В этапе 8 выполнены живые локальные команды на вымышленных файлах, неверные/верные ключи, два редактора, отсутствие исходника, отмена и ошибка записи; отдельные тесты покрывают сбой lock-снимка, очередь таймера, старый формат и сохранность аварийной копии при отказе новой записи. Точные счётчики и оставшиеся физические проверки — в [VALIDATION_STAGE8.md](../help/VALIDATION_STAGE8.md).
